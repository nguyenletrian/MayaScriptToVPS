# MayaScriptToVPS

Runtime/bridge layer between Maya applications and 3DVPSserver.

## Primary user flow

```text
3DVPSserver
    ↓ login
User activates an app
    ↓
Example: Maya Skin Tool
    ↓
Download generated .py bootstrap
    ↓
Drag the .py file into Maya
    ↓
onMayaDroppedPythonFile()
    ↓
Exchange short-lived bootstrap token
    ↓
Server checks user + app activation + permissions
    ↓
Return runtime session + manifest + runtime files
    ↓
Maya loads the app entrypoint
    ↓
Tool UI appears in Maya
```

The downloaded file is intentionally a small bootstrap, not the whole Maya tool library.

## Repository structure

- `bootstrap/maya_app_loader.py` — self-contained drag/drop bootstrap template generated by 3DVPSserver.
- `client/api.py` — small stdlib HTTP client for runtime/server communication.
- `app/manifest.py` — app manifest model and validation.
- `app/app_loader.py` — app permission/entrypoint loading boundary.
- `security/permissions.py` — runtime permission checks.
- `ui/` — Maya UI helpers.
- `maya_tools/` — server-facing Maya app entrypoints/wrappers.
- `registry/` — approved structured-command registry for remote execution when needed.
- `schemas/` — command/result payload helpers.
- `docs/server_contract.md` — API contract to implement in 3DVPSserver.

## Maya Skin Tool example

A runtime manifest can point to:

```json
{
  "app_id": "maya_skin_tool",
  "name": "Maya Skin Tool",
  "version": "1.0.0",
  "entry_module": "maya_tools.skin_tool_app",
  "entry_function": "show",
  "permissions": ["maya.scene.read", "maya.skin.write"]
}
```

The sample entrypoint in `maya_tools/skin_tool_app.py` creates a Maya UI and calls existing `NLTA_Skinning` functions rather than duplicating the tool implementation.

## Relationship with MayaScriptNew

`MayaScriptNew` remains the implementation/tool library for now. `MayaScriptToVPS` is the distribution, activation, runtime and server-integration boundary. Existing NLTA modules can be wrapped gradually per app instead of copying the whole codebase at once.

## Security model

3DVPSserver remains authoritative for app activation, session expiry, permissions, runtime version and revocation.

Code delivered to a user's computer cannot be considered secret. Do not embed long-lived server credentials in downloaded Python. Use short-lived bootstrap tokens, short-lived runtime sessions and server-side authorization instead.

## Legacy structured commands

The initial ToolRegistry/executor flow remains available for future server-driven commands:

```text
3DVPSserver → structured command → ToolRegistry → approved Maya function → result/error
```

This is secondary to the app activation/download/drag workflow, not the main entrypoint.
